## Архитектура и файлы

```text
src/main/java/ru/matsukov/raster/
  RasterApp.java       — JavaFX-интерфейс и обработчики
  ScanSession.java     — фоновый обход и ограниченный пул задач
  BinaryReader.java    — чтение байтов с кэшем, контроль границ
  ImageParser.java     — сигнатуры и парсеры шести форматов
  ImageInfo.java       — результат чтения одного файла
  CsvExporter.java    — безопасная запись CSV через временный файл
src/test/java/ru/matsukov/raster/
  ImageParserTest.java — автоматические проверки
  StressCheck.java     — отдельный синтетический тест больших файлов
samples/              — примеры для интерфейса
test-data/            — дополнительные тестовые изображения
pom.xml               — зависимости и сборка
```

`ImageParser.inspect()` открывает `BinaryReader` через try-with-resources: файловый канал закрывается и после успеха, и после ошибки. Reader проверяет смещение и длину до чтения, использует 64-битные размеры и кэш 4096 байт. PNG IDAT и прочие большие области пропускаются по длине; TIFF значения читаются по смещениям; JPEG читает заголовок и не более 64 КиБ хвоста для EOI. Маленькие изображения могут целиком попасть в кэш — это нормально.

`ScanSession` сначала перечисляет пути в фоновом потоке, затем запускает обработку. На стадии перечисления прогресс неопределённый; после получения количества файлов — точный. В пуле одновременно не более `2 × число потоков` отправленных задач. Очередь результатов ограничена 512 записями: если UI не успевает, координатор ждёт, а память не растёт за счёт бесконечного числа задач.

JavaFX Application Thread примерно каждые 150 мс забирает готовые результаты одной пачкой. `TableView` виртуализирует строки. Полный список путей и результатов хранится в памяти O(N), но изображения целиком не хранятся. UI не получает по одному `Platform.runLater` на каждый файл. Экспорт CSV выполняется отдельно от UI.

## Как извлекаются свойства

### PNG

Сигнатура: `89 50 4E 47 0D 0A 1A 0A`. Чанк: 4 байта длины, 4 байта типа, данные и 4 байта CRC. Все целые числа — big-endian.

- **IHDR**: ширина и высота, глубина одной компоненты/индекса и тип цвета. Типы 0/2/3/4/6 дают 1/3/1/2/4 компоненты соответственно. Глубина пикселя = bitDepth × число компонент. Для типа 3 хранится индекс палитры.
- **pHYs**: пиксели на единицу по X/Y. Только unit=1 задаёт метры: `DPI = pixelsPerMeter × 0.0254`.
- **PLTE**: RGB-тройки; число цветов = длина / 3.
- Сжатие — Deflate. Метод фильтрации 0 означает адаптивный выбор фильтров строк, а не отсутствие фильтрации. Из IHDR также читается interlaceMethod.
- Проверяются IHDR, допустимые комбинации типа/глубины, PLTE для индексированного изображения, IDAT, IEND и границы чанков. CRC и Deflate не вычисляются.

### JPEG

Сигнатура SOI — `FF D8`. Сегменты обходятся по маркерам и их 16-битным длинам.

- **SOF**: точность компоненты, высота, ширина, число компонентов. Глубина = точность × число компонентов (например, 8 × 3 = 24). Это не обязательно RGB: возможны YCbCr и CMYK.
- Тип SOF различает последовательный DCT, прогрессивный DCT и lossless JPEG.
- **APP0 JFIF**: units=1 — точки/дюйм, units=2 — точки/см, умножаем на 2.54. units=0 задаёт отношение плотностей, но не абсолютный DPI.
- **APP1 Exif**: вложенная структура TIFF; DPI берётся из XResolution, YResolution и ResolutionUnit, приоритет над JFIF.
- Нужны SOF, SOS и EOI `FF D9`. После начала скана сжатый поток не разбирается; EOI ищется в последних 64 КиБ файла.

### GIF

Заголовок GIF87a или GIF89a. Размер читается из Logical Screen Descriptor — это размер логического экрана, не отдельного кадра. По битам packed-поля определяется размер глобальной/локальных палитр: `2^(N+1)` цветов. Глубина — максимальная разрядность индекса среди найденных палитр. Палитра хранит RGB-тройки.

Сжатие — LZW. По длинам обходятся подблоки расширений и изображений, считается число кадров, проверяется завершающий байт `3B`. Абсолютный DPI в GIF не записан: PixelAspectRatio не заменяет DPI.

### TIFF

Первые два байта II/MM определяют little/big-endian, затем должно идти значение 42. Читается смещение первой IFD. Каждая запись IFD занимает 12 байт: tag, type, count, value/offset. Если данные помещаются в 4 байта, они находятся в самой записи; иначе это относительное смещение. Поддерживаются извлекаемые значения BYTE, SHORT, LONG и RATIONAL. Для прочих стандартных типов проверяются границы, но ненужные теги пропускаются.

| Тег | Значение |
|---|---|
| 256, 257 | Ширина и высота |
| 258, 277 | BitsPerSample и SamplesPerPixel: сумма бит компонент |
| 259 | Compression: без сжатия, CCITT, LZW, JPEG, Deflate, PackBits либо числовой код |
| 282, 283 | XResolution/YResolution — отношение двух UINT32 |
| 296 | ResolutionUnit: 2 — дюйм, 3 — сантиметр ×2.54, 1 — без абсолютных единиц |
| 273/279 | Смещения и размеры полос (strips) |
| 324/325 | Смещения и размеры плиток (tiles) |
| 320 | ColorMap — три массива R/G/B, число цветов = count / 3 |

Проверяются знаменатели RATIONAL, смещения, массивы strips/tiles и циклы IFD. Для нескольких страниц таблица показывает первую, а подробности — количество. В Exif смещения отсчитываются от начала вложенного TIFF. BigTIFF (magic=43) распознаётся отдельно как неподдерживаемый.

### BMP

Проверяются `BM`, BITMAPFILEHEADER и DIB. Поддерживаются BITMAPCOREHEADER (12 байт) и INFO-подобные заголовки размером от 40 байт.

Размер берётся из width и абсолютного height: отрицательный height означает порядок строк сверху вниз. Глубина — bitCount. Разрешение — положительные x/yPelsPerMeter × 0.0254. Сжатие — BI_RGB, BI_RLE8, BI_RLE4, BI_BITFIELDS и другие коды.

Палитра содержит RGBTRIPLE (B,G,R) для CORE или RGBQUAD (B,G,R,reserved) для INFO. `biClrUsed=0` у индексированного изображения означает полную палитру `2^bitCount`. Проверяются границы палитры, расположение пикселей, заявленный размер файла. Для несжатого изображения длина строки выравнивается до 4 байт: `stride = ceil(width × bits / 32) × 4`.

### PCX

Считывается 128-байтовый заголовок, первый байт — `0A`.

- ширина = xmax − xmin + 1; высота = ymax − ymin + 1;
- глубина = bitsPerPixel одной плоскости × nPlanes;
- DPI = hDpi/vDpi из файла, без попытки угадать реальные физические размеры;
- encoding=0 — без сжатия, encoding=1 — RLE;
- дополнительно показываются версия и BytesPerLine одной плоскости; проверяется, что строка не короче необходимого числа байт.

## Что означает статус OK

Это **проверка структуры и метаданных**, не полноценный декодер пикселей. Проверка обнаруживает неизвестные сигнатуры, многие усечения, выходы за границы, отсутствующие IEND/EOI/завершающий блок GIF, циклы IFD и ряд неверных полей. Один ошибочный файл не останавливает анализ остальных.

Ограничения:

- Не проверяются CRC PNG и содержимое сжатых Deflate/LZW/JPEG/RLE-потоков.
- Не проверяются абсолютно все семантические ограничения спецификаций.
- JPEG с более чем 64 КиБ хвостовых данных после EOI будет отмечен ошибкой.
- Редкий JPEG с высотой, задаваемой DNL после SOS, не поддерживается.
- BigTIFF и старые DIB размером менее 40 байт, кроме CORE 12, не поддерживаются.
- TIFF имеет защитные лимиты 10 000 IFD и 1 000 000 значений на извлекаемый тег; SubIFD-миниатюры не обходятся.
- Полное содержимое всех палитр не выводится; показывается количество цветов.
- Файлы, изменённые другим процессом во время анализа, могут получить ошибочный статус; анализировать лучше стабильную папку.
- Недоступные каталоги не обходятся; предупреждение отображается в строке состояния.

Дополнительно выполнен `StressCheck`: **600 разреженных синтетических файлов**, логический объём **2 100 000 000 байт**, считано **41 779 200 байт**, ошибок структуры 0. В среде проверки время чтения — 0.134 с, без создания образцов. Это искусственные файлы с JPEG-заголовком, пустым пространством и EOI; они проверяют чтение по смещениям и ограниченные очереди, **не являются реальными фотографиями и не доказывают такую скорость на диске пользователя**.

Повторить синтетический тест после `mvn test`:

Windows:
```bat
java -cp "target/classes;target/test-classes" ru.matsukov.raster.StressCheck
```
Linux/macOS:
```sh

```

Тест временно создаёт разреженные файлы с логическим объёмом 2.1 ГБ и затем удаляет их. На файловых системах без поддержки разреженных файлов может потребоваться соответствующее свободное место.

Архив преподавателя проверен: все 24 BMP успешно проходят TeacherFilesTest. Реальный стресс-тест на папке из 600 JPEG размером ~2 ГБ еще нужен. Не утверждается, что приложение испытано на реальной папке из 100 000 файлов. Визуальные проверки JavaFX и EXE на Windows также следует выполнить на целевой системе.

## Краткие ответы для защиты

1. **Зачем ручной парсинг?** Чтобы получать свойства из структур форматов и выполнять дополнительное условие задания, не используя готовый декодер метаданных.
2. **Почему быстро?** Чтение заголовков и небольших областей по смещениям, без декомпрессии пикселей.
3. **Почему окно не зависает?** Обход и чтение вынесены из JavaFX Application Thread; результаты передаются ограниченными пачками.
4. **Почему нет DPI?** В файле могут быть только пиксели или пропорции; 72/96 DPI нельзя придумывать.
5. **Почему GIF 2/4/8 бит, хотя цвета RGB?** Пиксель содержит индекс палитры, а не три компоненты RGB.
6. **Что такое RATIONAL?** Два целых числа: числитель и знаменатель; знаменатель проверяется на ноль.
7. **Как обнаруживается подмена расширения?** Формат определяется по magic bytes, расширение сравнивается только после разбора.
8. **Почему OK не гарантирует все пиксели?** Быстрая структурная проверка не распаковывает сжатый поток.
9. **Временная сложность?** O(N + сумма просмотренных блоков и значений TIFF); сортировка O(N log N). Память списка O(N); число одновременно открытых файлов ограничено пулом.

## Использованные средства и источники

- JDK 17: FileChannel, ByteBuffer для тестовых данных, ExecutorService, Files.walkFileTree.
- JavaFX 17.0.12: стандартный интерфейс без CSS; Maven-плагин JavaFX 0.0.8: запуск и runtime.
- JUnit Jupiter 5.11.4: только тесты, не входит в приложение.
- Тестовые растровые образцы были сгенерированы отдельно с Pillow; Python/Pillow не требуются для запуска проекта и не участвуют в его парсинге.

- PNG: https://www.w3.org/TR/png/ — IHDR, pHYs, PLTE, IEND.
